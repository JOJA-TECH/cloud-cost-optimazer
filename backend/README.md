# Backend persistence

This module is the persistence adapter for `cco_app`. It is intentionally kept separate from the frontend and from domain/application contracts.

## Structure

```text
backend/
├── go.mod
└── internal/
    ├── iam/
    │   └── user.go                         # DTOs + repository contract/adapter
    └── platform/database/
        ├── database.go                     # driver config and schema qualification
        ├── migrate.go                      # GORM migration entry point
        ├── models.go                       # persistence-only models
        └── database_test.go                # SQLite portability test
```

The model set covers the 21 tables currently in `databases/cco_app/cco_app.sql`, distributed across `iam`, `organization`, `cloud`, `app` and `audit`.

## Portability rules

- Application code depends on repository interfaces and DTOs, never on GORM models.
- SQLite uses unqualified table names; PostgreSQL uses the existing five schemas. The decision is isolated in `database.TableName`.
- JSON data uses `gorm.io/datatypes`, not PostgreSQL-only JSON types in application code.
- UUIDs are generated by Go at the repository boundary, so SQLite does not need `pgcrypto`.
- PostgreSQL-specific schema creation is isolated in `Migrate`; the domain and repositories remain dialect-neutral.
- The existing PostgreSQL dump remains the production reference for RLS, check constraints, indexes, triggers, extensions and foreign keys. GORM migration is intended for local/test bootstrap and incremental application-owned changes; it must not silently replace security policies.

## Run tests

```bash
go test ./...
```

The first migration target is SQLite for fast isolated tests. PostgreSQL can be selected with `database.DriverPostgres` and a normal PostgreSQL DSN. The same models and repositories are used in both cases.
