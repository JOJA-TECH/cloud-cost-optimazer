## Temas tratados

### Tema y título del proyecto

- Plataforma inteligente para análisis y optimización de costos de bases de datos en la nube (`Azure SQL Database`) mediante monitoreo, analítica predictiva y recomendaciones de capacidad.
- Título definitivo pendiente de precisar; se descartó el enfoque genérico de "costos en la nube" (workload).

### Pregunta de investigación e hipótesis

- Es crítico definirlas bien para justificar el proyecto ante el profesor.
- Se adoptan de momento la pregunta de investigación y la hipótesis propuestas por el análisis con IA; deben validarse con el profesor Aisner antes de avanzar.

### Plazos y entregas

- Primer avance: 14 de septiembre de 2026 (problema, justificación, objetivos, usuarios beneficiados, alcance preliminar, antecedentes).
- MVP: 26 de octubre de 2026 (al menos un flujo E2E: registro, login, guardado en BD).
- Entrega final: finales de noviembre de 2026 (~4 meses).

### Arquitectura general

- Frontend: aplicación web tipo dashboard (reportes y recomendaciones). Pendiente: elegir entre Next.js y Flutter.
- Backend: API Gateway en Go (autenticación, gestión de BD, orquestación, recomendaciones).
- Módulo ML como servicio independiente; arquitectura simple de 2 microservicios.
- Capa de abstracción con modelo de datos común y conectores/providers por proveedor cloud (Azure/AWS/GCP preparados).
- Infraestructura: PostgreSQL; laboratorios (datos sintéticos) con Terraform; evaluar S3 y CloudFront; Redis solo como opción para sesiones del lado del cliente.
- Reportes: no se guardan como archivos; se almacena la información/resultado en BD y el PDF se genera en tiempo de ejecución (pendiente: backend o frontend).
- Almacenamiento: sin bucket; archivos, modelos y reportes se gestionan vía GitHub.
- Autenticación: proveedor externo (Supabase u otro, o servicios de Azure/AWS); el usuario provee su propia API key del proveedor cloud.

### Módulo de Machine Learning

- Componentes: forecasting, detección de anomalías, modelo de capacidad, optimizador de escenarios, cálculo de riesgo y explicación generativa (LLM).
- Chat/asistente: reutilizar el mismo motor de explicaciones generativas; se descarta chat con memoria propia.
- Opción abierta (propuesta de Jesús): proveedor de modelo configurable por el usuario (local o externo).
- Reentrenamiento periódico solo si hay una cantidad mínima de datos nuevos.
- Los reportes del módulo de ML se guardan en BD (posible vectorización futura).

### Alcance, prioridades y descartes

- MVP: flujo E2E completo, backend ~50-60% avanzado, frontend inicial y datasets de laboratorios.
- Segundo plano: detección de anomalías, optimización de escenarios, reportes/simulaciones.
- Descartadas: notificaciones.

### Auditoría y trazabilidad

- El usuario final podrá ver el historial de acciones y recomendaciones recibidas.
